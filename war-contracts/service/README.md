# Bound Google Sheets service

Copy `Code.gs` into **Extensions → Apps Script** from the intended workbook. Save, reload the workbook, then choose **War Contracts Service → Configure faction service**. Enter our public `FACTION_ID` once. Setup obtains this bound workbook's ID itself and stores it in Script Properties for deployed requests; no ID is embedded in this package. The ranked war and opponent are detected automatically, including scheduled wars. Old `WAR_ID`/`OPPONENT_ID` properties are ignored. Setup creates only `Script Contracts` and `Script Contract Registry` if absent. Do not rename these service-owned sheets or edit their rows.

Review configuration, authorize the bound project, then deploy a web app executing as the workbook owner with access appropriate for participating faction members. Copy the deployment `/exec` URL into the userscript Connection section. Deployment/public access and Google grants must be approved by the workbook owner; local tests do not deploy or write the real workbook. Updating source requires publishing a new deployment version. The current ranked war is detected automatically; mutation requests carrying a stale war ID are rejected.

Confirmed output is also copied into blank compatible cells in the original `War Contracts` tab. Header support includes blank-only filling of D6 (opponent) and E6 (TCT start) for the detected scheduled/current war. Existing values (including `-`), formulas and formatting are preserved; only the public contract fields described below may also be filled. A conflicting opponent heading blocks filling and normal service actions. Its header is D9:L9, with entries from row 10: D our member, E private stats (ignored), F online window, G hits, H/I opposing target(s), J time, K Warlord, L notes. D6 supplies the opponent display name and I6 the positive maximum hit count. Each populated target produces a public contract. IDs resolve from profile links, `[id]` display text, or exact case/whitespace-normalized roster names. Unresolved names remain visible and block exact name matches. Existing contract values, notes, formulas and formatting are preserved. Manual edits cannot acquire the script lock; the next board/reserve/confirm read detects them, but no system can discover unrecorded private agreements.

`Script Contracts` is append-only confirmed output; `Script Contract Registry` holds pending state. Columns A:K contain stable record ID, war ID, our member, enemy, status, hits, online window, time, Warlord, notes, and authoritative record JSON. JSON includes only public identities, terms and operation metadata. No key, private stats, gear, or complete Torn response is stored. Formula-leading text is escaped and ranges are formatted as text. Keep row IDs/JSON intact: confirmation recovery reads output first, so an append that succeeded before a timeout or registry failure is recovered without another append.

## Main table copy

After the audit append succeeds, `syncMainContract(record, rosters)` fills D/F/G/H/J/K/L in one compatible member row or an unused row. E (private stats) and I (second target) are never written. An existing exact pair in H or I is recognized for retries. Different bookings or incompatible terms block the copy. Blank-returning formulas and cell annotations are protected. A full table adds one row with formatting and validations only. Reads are bounded to 10,000 body rows.

Registry-only `mainSheetSynced`, `mainSheetRow` and allowlisted `mainSheetError` track partial-copy recovery without altering the canonical confirmation. `board` may finish only the verified caller's confirmed current-war copy after fresh war verification. Ended/changed wars are read-only. A completed copy is never rewritten; later differing manual edits remain visible alongside the audit record. Compatible main/audit pairs appear once in Current Contracts. Direct human edits do not take the script lock; cells are rechecked immediately before writing, but Sheets provides no atomic conditional write against simultaneous manual edits.

## JSON contract

POST a JSON body with `action` and `apiKey`. `board` needs no other fields. Every mutation requires numeric `warId` matching the current board:

- `reserve`: UUID `requestId`, positive numeric `enemyId`. Retain the UUID across uncertain retries. Reusing it for another owner/target fails.
- `sent` / `release`: owned pending `id`. Release cannot alter manual or confirmed deals. Pending contacts never expire automatically.
- `confirm`: owned `id`, integer `hits` from 1 through sheet maximum, strings `onlineWindow` (120 characters), `time` (80), `warlord` (80), `notes` (1000), and literal `strippedConfirmed: true`. The client must show a preview and require explicit agreement attestation. Exact retries are safe; changed terms under the same confirmation identity fail.

Success: `{ok:true,user,context,contracts,deal?}`. `user` is `{id,name,factionId}`. `context` is `{warId,factionId,opponentId,opponentName,maxHits,ended}`. Contract fields are `{id,ourId,ourName,enemyId,enemyName,status,source,hits,onlineWindow,time,warlord,notes,createdAt,updatedAt}`; manual unresolved IDs can be null. Confirmed script records also expose boolean `mainSheetSynced` and allowlisted `mainSheetError`; a failed main copy does not undo confirmation. Sources are `manual`/`script`; statuses are `manual,reserved,contacted,confirmed,cancelled`. Error: `{ok:false,error:{code,message}}` with allowlisted codes. Treat `UNAVAILABLE` as uncertain and refresh the board before retrying; a transport timeout is never confirmation of success.

Caller identity comes from Torn v2 `key/info` (`info.user.id` and `faction_id`), then membership/name from the configured faction roster; target membership comes from the configured opposing roster. Browser identity/name claims are ignored. Official schema: [Torn OpenAPI](https://www.torn.com/swagger/openapi.json). Torn receives the key through an Authorization header. Only SHA-256 credential fingerprints index the short identity cache; raw keys remain in request memory. Sanitized public rosters/identities cache for 30 seconds. Per-credential 30/minute and global 240/minute bounds protect Torn calls; Apps Script cache eviction means these are best-effort rate bounds rather than a billing/security perimeter. Body size is capped at 16 KiB, public rosters at 1,000 entries, and sheet row reads at 10,000. Authentication/config/fetch errors fail closed without raw error details or logging.

## Test seam and checks

`createWarContractsService(deps).handle(payload)` is synchronous. Dependencies: `config`; `authenticate(apiKey)`; `verifyContext(apiKey,config,fresh) → {warId,factionId,opponentId,opponentName,ended} | null`; `rosters(apiKey,config) → {ours,enemies,opponentName?}`; `readManual(rosters) → {maxHits,opponentName,contracts}`; `readRecords() → {records,confirmed}`; `writeRecord(record)`; `appendConfirmed(record)`; `syncMainContract(record,rosters)`; `lock(callback)`; `now()`; `id()`. Every transition and fresh manual/output read occurs under the supplied lock. Production uses `LockService.getScriptLock()`.

Run `node --test war-contracts/test/service.test.cjs`. Node VM parses the actual `.gs` source and exercises synthetic sheet/state fixtures, including stale-war rejection, own-row authority, reservation conflicts, manual additions, exact retries, uncertain append recovery, strict terms, preserved manual reads, blank-only main-table writes, formatted numeric hits and interrupted-copy recovery. No authenticated Torn requests or real workbook writes occur. Live deployment, concurrent Apps Script execution, Google permission grants and real workbook validation remain separate acceptance checks.


The service discovers the ranked war through Torn `faction/{FACTION_ID}/wars`, reading `wars.ranked.war_id`, `factions` and nullable `end`. It verifies our configured faction is a participant and derives the other faction's ID/name from Torn. Scheduled wars are available for advance deals. If `wars.ranked` is null, the first item from `faction/{FACTION_ID}/rankedwars?limit=20` is allowed only if ended, for read-only access to the previous war. No current/history entry returns `NO_WAR`. Only sanitized identifiers, own/opponent faction names, start/end timestamps and the ended flag cache for 30 seconds on board reads; every mutation bypasses the discovery cache under the script lock. Sheet D6 must exactly match the detected opponent name after case/whitespace normalization (and optional `[id]` removal), otherwise `CONFIG` prevents actions against a stale manual tab. Registry and confirmed output are scoped to the exact war/faction/opponent tuple. Changed-war mutations return `CONTEXT_CHANGED`; an ended war returns `WAR_ENDED`. Public opponent names come from Torn rather than the client or sheet heading. Context also exposes `factionName`, `startAt` and `endAt` (Unix seconds or null), allowing clients to show TCT defaults without extra API calls. Header filling runs inside the existing script lock and bypasses the discovery cache whenever a header needs filling; no header is filled for an ended war. Manual users do not acquire this lock, so blank checks are a best-effort concurrency guard rather than an atomic conditional Sheet write.

Contracts also expose boolean `confirmationPending`: true only when immutable confirmation terms have been saved but the pending contact has no confirmed output yet. Before attempting the append, the registry saves all validated terms plus their canonical signature while retaining its pending status. A board reload therefore restores the exact hits/window/time/Warlord/notes for retry even if append failed before writing anything. The UI must retain the same deal ID and recovered terms; it must not silently replace an uncertain operation with edited terms. Formula-like text may appear with its protective leading apostrophe in recovered terms; sending those exact canonical strings is idempotent and does not add another apostrophe. Confirmed/manual/unprepared records return `confirmationPending: false`.
